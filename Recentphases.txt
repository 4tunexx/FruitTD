   ==================================================

* Purchase-only hero
* Cost must come from one central configurable value

Master Ki

* Never automatically unlocked
* Purchase-only hero
* Cost must come from one central configurable value

* XP must persist after reload.

# FruitTD — Slicer / Blade VFX Overhaul

## IMPORTANT

Do not just change colours, glow values or CSS.

The current slicer visual implementation is fundamentally wrong for the intended game feel.

I inspected the current implementation and found:

* `src/game/slashfx.ts` uses `RingGeometry`, creating circular hit effects.
* `src/game/trail.ts` uses Three.js `Line` objects for the blade trail.
* `src/input/blade.ts` records multiple swipe samples but `consumeSlash()` collapses the entire swipe into one `first → last` line.
* The current slicer system therefore looks more like glowing circles/lines than a proper game blade.
* `src/ui/slicerPreview.ts` currently previews the slicer using DOM/CSS and also needs to be upgraded to represent the real in-game effect more accurately.

The target is NOT to copy Fruit Ninja's exact assets.

The target is the same general quality of blade feedback:

**smooth → sharp → tapered → curved → fast → satisfying → readable**

FruitTD must have its own visual identity.

---

# 1. REMOVE THE CIRCULAR SLASH LOOK

The existing `RingGeometry` hit flash in:

`src/game/slashfx.ts`

must NOT be the primary slice effect.

Do not make the blade look like:

* circles
* rings
* bubbles
* glowing discs
* circular shockwaves
* simple neon lines

A small impact burst can still exist as a secondary hit effect, but the main slicer visual must clearly read as a **blade cutting through the screen**.

---

# 2. BUILD A REAL BLADE RIBBON

Replace the current simple Line-based trail with a proper dynamic ribbon/trail mesh.

The blade should be generated from the actual swipe history.

Conceptually:

POINT 1
\       taper
____
________
____
\

The trail needs:

* multiple historical points
* smooth interpolation
* rounded/continuous curve
* variable width
* tapered front and rear
* alpha fading
* short lifetime
* no gaps at high swipe speed
* no visible polygon/jagged stepping

Use a dynamic BufferGeometry / ribbon mesh or equivalent Three.js implementation.

Do NOT use hundreds of individual sprites.

The trail should be performant.

---

# 3. TRACK THE ENTIRE SWIPE

The current `BladeInput.consumeSlash()` is a major part of the problem.

It currently takes the first and last points and effectively turns a curved swipe into one large straight segment.

Fix this.

The system needs to preserve the swipe path.

Instead of:

first → last

use:

P0 → P1 → P2 → P3 → P4 → P5 → ...

Then smooth/interpolate those points before rendering.

The gameplay hit detection and the visual trail should both understand the actual swipe path.

Do not sacrifice gameplay collision accuracy.

---

# 4. SEPARATE INPUT FROM VISUAL TRAIL

Create a clean separation:

### BladeInput

Responsible for:

* pointer/touch tracking
* raw movement samples
* swipe segments
* velocity
* charge
* pointer type

### BladeTrail

Responsible for:

* visual history
* smoothing
* ribbon generation
* tapering
* fading
* glow
* slicer style

### SlashFx

Responsible for:

* hit spark
* fruit impact
* juice burst
* critical hit effect
* special enemy impact

This should prevent the current situation where one simple visual object is expected to represent everything.

---

# 5. MAKE THE TRAIL LOOK LIKE A BLADE

The visual shape should have at least three layers.

## Layer 1 — Core

Very bright, thin central blade edge.

Example:

white / pale version of slicer colour

It should be sharp and readable.

## Layer 2 — Main blade body

A wider tapered ribbon following the swipe.

Uses the slicer's primary colour.

## Layer 3 — Soft glow

A wider, lower-opacity version behind the blade.

Uses `glowColor`.

The result should visually read as:

bright sharp edge
+
coloured blade body
+
soft energy glow

NOT:

blue line
+
blue line
+
circle

---

# 6. TAPER THE TRAIL

The blade should NOT have the same width from beginning to end.

Use something similar to:

START
0% width

→

15%
medium

→

40%
full width

→

70%
medium

→

100%
tiny/faded

This creates a proper sword/blade movement impression.

The leading edge should remain sharper/brighter.

The oldest points should disappear quickly.

---

# 7. SMOOTH THE MOVEMENT

Do not simply draw the raw pointer coordinates.

Use interpolation / smoothing.

Possible approaches:

* Catmull-Rom interpolation
* cubic interpolation
* moving average
* resampling by distance
* Hermite interpolation

Choose the method that gives the cleanest result at 60 FPS.

The important thing is:

FAST SWIPE:

must remain smooth.

SLOW SWIPE:

must remain smooth.

CURVED SWIPE:

must remain curved.

SMALL SWIPE:

must not create ugly spikes.

---

# 8. PREVENT TRAIL GAPS

This is extremely important on mobile.

If the player moves:

P1 ---------------------------- P2

the trail must fill the entire distance.

Never render only one point per pointer event.

Resample/interpolate long distances so the ribbon remains continuous.

The visual result should never have:

* broken segments
* dotted trail
* gaps
* disconnected pieces
* sudden jumps

---

# 9. TRAIL LIFETIME

The blade trail should feel fast.

Target approximately:

0.15–0.35 seconds

for the visible trail.

Do not make it hang around for 1+ seconds.

The trail should:

APPEAR FAST
→
BRIGHT
→
TAPER
→
FADE
→
DISAPPEAR

The player should feel like they physically swung a blade through the scene.

---

# 10. VELOCITY RESPONSE

Blade width and brightness should respond to swipe speed.

Slow movement:

* thinner
* lower glow
* less dramatic

Fast movement:

* slightly wider
* brighter
* stronger glow
* stronger spark emission

Do not make fast movement ridiculously thick.

Keep it controlled.

---

# 11. CURVED SLASHES

A major requirement.

If the player makes:

/

then the blade should look like:

/

If they make:

)

the trail should look like:

)

If they make:

the trail should visually follow the S curve.

Do NOT flatten the entire swipe into one straight line.

---

# 12. HIT EFFECT

Keep an impact effect, but completely change its role.

Current:

`RingGeometry`

should no longer be the main hit visual.

Instead create a directional slice impact.

When a fruit is hit:

* tiny bright cut flash
* 3–8 small sparks
* juice particles
* directional streaks
* tiny impact burst
* optional micro screen shake
* optional very short hit-stop

The particles should travel primarily along the slash direction and slightly outward.

They should NOT form a perfect circle.

---

# 13. FRUIT SLICE EFFECT

1. blade passes through fruit
2. tiny bright cut flash
3. fruit halves separate
4. juice sprays outward
5. 2–8 tiny droplets/sparks

7. blade continues naturally

The visual should make the player feel that the blade actually cut the fruit.
